# 코드 리뷰 가이드라인

## 리뷰 절차 — 4단계 모두 확인

변경 내용을 아래 4단계로 나누어 검토한다. 각 단계마다 코멘트를 남기거나 명시적으로 "문제 없음"이라고 판단한다. 첫 단계만 보고 멈추지 말고, 4단계를 모두 끝낸 뒤 리뷰를 마무리한다.

1. **정확성**: 버그, 기존 동작 회귀, 런타임 오류, 불가능한 상태, 누락된 에러 처리, 데이터에 대한 불안전한 가정, 비동기·상태 업데이트 위험, 경쟁 상태(예: mutation 대기 중 이중 submit).
2. **프로젝트 규칙**: 아래 규칙 위반 여부. 이 규칙들은 객관적 기준이므로 항상 코멘트할 수 있다.
3. **React 상태/effect**: 계산 가능한 파생 값을 상태에 저장했는지, `useEffect` 의존성이 올바른지, 오래된 값이나 불필요한 재실행이 있는지, 이벤트·타이머·구독·STOMP/socket handler 정리가 있는지, 이전 상태 기반 업데이트에 함수형 `setState`가 필요한지, 렌더링에 영향 없는 일시 값을 상태 대신 ref에 둬야 하는지, 컴포넌트 안에 컴포넌트를 정의했는지 확인한다.
4. **UX 상태**: 로딩, 오류, 빈 상태, 데이터 없음 처리가 있는지, 사용자 노출 문구가 한국어이며 대체 문구가 있는지, 상호작용 요소에 disabled/pending 상태가 있는지 확인한다.

**얕은 리뷰 자가 점검**: 변경 내용이 100줄을 넘는데 구체적인 코멘트가 2개 미만이면, 할 말이 없다고 결론 내리기 전에 2단계와 3단계를 다시 확인한다. 개수를 맞추려고 약한 코멘트를 억지로 만들지는 않는다.

## 프로젝트 규칙 (2단계 기준)

전체 규칙은 `.codex/instructions/*.md`에 있다. 이 규칙에 근거한 코멘트는 **개인 취향이 아니다.** 필요한 경우 반드시 남긴다. 핵심 규칙은 아래와 같다:

- 모든 HTTP 요청은 TanStack Query를 통한다. `mutateAsync` + try/catch, 또는 컴포넌트/핸들러에서 HTTP `fetch`/`axios`/`client.*`를 직접 호출하는 것은 위반이다. STOMP publish/subscribe는 제외한다. 성공/실패 처리는 `onSuccess`/`onError`에서 한다. (.codex/instructions/api.md)
- API 함수는 사용 범위에 맞는 `apis/`에 두고, 파일 하나에 함수 하나만 둔다. 페이지 전용 API는 `pages/<page>/apis/`, 여러 페이지에서 쓰는 도메인 API는 `domain/<domain>/apis/`에 둔다. 이름은 `createGame`이 아니라 `postGames`처럼 HTTP 메서드 + 리소스로 짓고, `common/api/client` 래퍼와 제네릭 2개를 모두 사용한다.
- 색상, 타이포그래피, border, radius, shadow는 `THEME`(`src/common/styles/theme.ts`)에서만 가져온다. styled 블록 안의 하드코딩된 hex, `font-family`/`font-size`/`font-weight` 직접 선언은 위반이다. `px` 단위도 위반이며 `rem`을 쓴다. (.codex/instructions/styling.md)
- import 방향은 `pages → domain → common`이다. `common`이 `domain`/`pages`를 import하거나, `domain`이 `pages`를 import하거나, 페이지끼리 import하는 것은 위반이다. (.codex/instructions/folder-structure.md; 앞의 두 항목은 ESLint error이기도 하다)
- 새 공유 코드는 기본적으로 `pages/`에 둔다. `domain`/`common` 승격은 실제 사용처가 2곳 이상일 때만 한다. 성급한 승격과 추상화는 지적한다. (.codex/instructions/folder-structure.md)
- 한 파일에는 컴포넌트를 하나만 둔다(`S_` styled 컴포넌트 제외). JSX를 반환하는 `renderXxx` helper function도 두 번째 컴포넌트로 본다. styled 컴포넌트는 파일 하단에서 `S_` prefix를 쓴다. (.codex/instructions/components.md)
- 핸들러는 내부 함수 `handleXxx`, 콜백 prop `onXxx`, 이벤트 파라미터 `e`를 사용한다.
- 컴포넌트 내부 순서는 라이브러리 훅 → 상태 → query/mutation → 파생 값 → handler → effect → JSX를 따른다. 관련 상태+handler 묶음이 크면 순서를 섞지 말고 custom hook으로 추출한다.
- 이 프로젝트에는 테스트 러너가 없다. 테스트 파일을 요청하지 말고, 위험한 변경에는 스크린샷이나 재현 절차 같은 검증 증거를 요청한다.

## 리뷰 초점 (1단계와 4단계 참고)

- 구현이 PR 설명과 연결된 이슈에 맞는지 확인한다.
- 보안, 개인정보, 인증, 인가, 민감 정보 노출 문제가 있는지 확인한다.
- 변경 범위가 PR 목표에 비해 불필요하게 넓지 않은지 확인한다.
- 코드가 이해, 수정, 검증하기 불필요하게 어려운지 확인한다.
- 중복 로직이나 불명확한 책임 경계가 실제 유지보수 위험을 만드는지 확인한다. 단, 이 프로젝트는 함께 바뀌어야 하는 복사가 아니면 성급한 추상화보다 중복을 선호한다.
- 큰 라이브러리나 무거운 컴포넌트가 초기 번들에 불필요하게 포함되는지 확인한다.
- 컴포넌트 props가 명확한 API를 이루는지, 부모/자식 사이 상태 소유권이 명확한지 확인한다. props 변경 제안은 현재 props가 책임을 흐리거나, 비즈니스 로직을 중복시키거나, 동작 불일치 위험을 키울 때만 한다.

## 리뷰하지 않을 것

- ESLint/Prettier/tsc가 CI에서 실제로 보고하는 포맷, import 순서, 미사용 import에는 코멘트하지 않는다. 단, 도구가 실제로 잡는 것만 제외한다. 도구가 잡을 수도 있다는 이유만으로 제외하지 않는다.
- 개인 취향이나 대체 스타일만 근거로 코멘트하지 않는다. (`.codex/instructions/*.md` 규칙이나 4단계 검토에 근거한 코멘트는 개인 취향이 아니다.)
- PR, 연결된 이슈, 코드에 설명되지 않은 비즈니스 의도를 단정하지 않는다. 대신 질문한다.
- PR 범위를 벗어난 큰 리팩토링을 요청하지 않는다.

## 코멘트 스타일

- 모든 리뷰 코멘트는 한국어로 작성한다.
- 모든 코멘트 앞에 심각도 라벨을 붙인다:
  - `🔴` — 병합 전 필수 수정(버그, 회귀, 보안, 런타임 영향이 있는 규칙 위반)
  - `🟡` — 선택 제안(런타임 영향이 없는 규칙 위반, 유지보수성, 가독성)
  - `💬` — 질문 또는 확인이 필요한 가정
- `🟡` 코멘트는 구체적이고 실용적이면 남긴다. `🟡`의 기준을 낮추려는 의도는 맞지만, 개수를 채우려고 코멘트를 만들지는 않는다.
- 각 코멘트는 문제 → 영향 → 실용적인 수정 방향을 포함한다. 가능하면 발생 조건이나 재현 흐름도 함께 적는다.
- PR 전체 코멘트보다 관련 줄의 인라인 코멘트를 우선한다. 높은 심각도부터 나열한다.
- 가정에 근거한 코멘트는 `💬`로 표시하고 어떤 증거를 확인해야 하는지 적는다.
- 4단계가 모두 문제 없을 때만, 어떤 단계를 확인했는지와 조치할 이슈가 없다는 사실을 한국어로 말한다. 코멘트를 하나라도 남겼다면 이 요약은 쓰지 않는다.
